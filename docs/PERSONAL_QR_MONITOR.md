# 个人收款码：到账实时监控与自动确认

## 1. 问题：为什么拿不到到账状态

个人收款码（微信 / 支付宝「收钱码」）与商户号渠道的本质差异：

| | 商户号渠道（微信支付 / 支付宝当面付） | 个人收款码 |
| --- | --- | --- |
| 资金路径 | 付款人 → 渠道受控账户 → 结算给商户 | 付款人 → **直接进个人零钱 / 余额** |
| 渠道回调 | 有（官方异步通知 + 查单接口） | **没有**，且不存在官方开放 API |
| 账单 | 可下载对账单 | 只能在 App 内查看，无 API |

钱不经过支付中心、也不受渠道受控账户管理，**渠道无从通知我们**。所以「到账状态」只能由**能看到钱的人**提供——这就是「监控器」的角色。

## 2. 架构：监控器 + 入站事件 + 自动匹配

```
微信/支付宝收款通知（手机端）
        │  监听
        ▼
   监控器（端侧 App / 网关程序）
        │  解析出：金额、备注、时间、流水号
        │  POST /api/v1/open/qr/payment-report（AppSecret 签名）
        ▼
   payment_incoming_event（入站事件，serial 幂等）
        │  匹配引擎
        ▼
 命中唯一订单 → paymentService.markPaid → 订单 SUCCESS → 异步通知业务系统
 无法唯一命中  → 挂账（UNMATCHED / AMBIGUOUS）+ 邮件告警 → 后台人工绑定
```

关键点：**置成功与通知走的是全渠道通用的 `markPaid`**，与微信/支付宝回调进来完全同一条代码路径，业务系统收到的回调报文、签名、重试策略零差异。

## 3. 上报接口

`POST /api/v1/open/qr/payment-report`
鉴权：`ApiSignGuard`（`X-App-Id` / `X-Timestamp` / `X-Nonce` / `X-Sign`），与下单退款同一套签名。

请求体：

```json
{
  "accountType": "wechat",        // wechat / alipay / other
  "amount": "100.00",             // 实收金额（元）
  "serial": "wx-20260920-0001",   // 监控器侧唯一流水号（幂等键，必填）
  "remark": "123456",             // 付款备注（付款人填的订单号后 6 位）
  "payerAccount": "张**",          // 付款方昵称/账号
  "paidAt": "2026-09-20T12:34:56+08:00",
  "raw": { "notifyText": "微信支付收款到账通知 ￥100.00" }
}
```

响应：`data.event.matchStatus`

| matchStatus | 含义 | 后续 |
| --- | --- | --- |
| `MATCHED` | 已自动匹配订单并置成功 | 已通知业务系统 |
| `UNMATCHED` | 时间窗内没有金额相符的待付订单 | 挂账 + 告警，后台人工绑定 |
| `AMBIGUOUS` | 同额订单多笔，不敢自动认领 | 挂账 + 告警，后台人工绑定 |
| `PENDING` | 自动确认已关闭 | 后台人工绑定 |
| （`duplicate: true`） | serial 重复上报 | 已忽略，安全 |

其它接口：

- `POST /api/v1/open/qr/payment-report/text` —— **通知/短信原文上报**（端侧不解析，支付中心解析；`?dryRun=1` 只解析不落库）
- `POST /api/v1/open/qr/payment-report/batch` —— 批量补推（最多 200 条）
- `GET  /api/v1/open/qr/payment-events` —— 商户自查挂账事件
- `POST /api/v1/open/pay/confirm-paid` —— **商户自助确认到账**（商户在自己系统里核对账单后调用，仅个人码渠道，必须传 `paidAmount` 且与应付一致）
- `GET  /api/admin/personal-qr/events` —— 后台挂账清单
- `POST /api/admin/personal-qr/events/:id/bind { payOrderNo }` —— 人工绑定并补发通知

## 4. 匹配策略（由强到弱）

1. **备注尾号**：收银台提示付款人「付款备注填订单号后 6 位」，监控器解析备注 → 精确命中（`matchedBy=remark`）
2. **唯一金额识别码**（可选开关 `personalQr.uniqueAmount`）：应付金额 = 订单金额 + `0.01~0.90` 元识别码，使到账金额本身成为订单唯一键，**即使不填备注也能 100% 自动匹配**；代价是付款人多付几分钱
3. **金额 + 时间窗**：同额多单时，若只有一笔「已申报」（付款人点过「我已完成支付」）则认领它，否则判 `AMBIGUOUS`

> 铁律：**匹配不上绝不猜**。宁可挂账人工处理，也不能把 A 的钱记到 B 的订单上。

## 5. 监控器怎么落地（三档，按成本从低到高）

### 5.1 零开发：通知 / 短信转发（推荐先用这个）

不用写任何代码。在收款手机上装一个「能转发通知或短信到 HTTP」的工具，把到账通知原文丢给支付中心，剩下的（解析金额、匹配订单、置成功、通知业务系统）全在服务端完成。

```
微信「收款助手」/支付宝/银行到账通知
        │  手机端转发工具（Tasker / MacroDroid / 短信转发器等）
        │  POST {baseUrl}/api/v1/open/qr/payment-report/text?token=mt_xxx
        │  body: { "text": "微信支付收款到账 100.01 元（来自*三）" }
        ▼
   支付中心解析（金额 / 账户类型 / 付款方 / 时间）→ 匹配 → 置成功 → 通知业务系统
```

配置要点：
- 后台「个人收款码 → 生成监控器 Token」拿到 `token`，接口会直接给出可复制的完整 URL。
- 触发条件：通知标题/内容包含「收款」「到账」「入账」等词（避免把付款通知也转上来）。
- 只支持微信/支付宝/银行三类文案；特殊文案可在后台配置 `personalQr.textAmountRegex` 自定义金额抽取。
- 先用 `?dryRun=1` 试一次，确认解析出的金额对得上再正式启用。

**防资损**：微信/支付宝的通知有「收款」和「付款」两种、长得极像。服务端只认收款语义词，纯「付款/支出/消费/扣款」文案一律拒绝并报错，绝不会把支出记成收入。

### 5.2 轻量开发：Android 通知监听 App

自建 `NotificationListenerService`（无需 root）读系统通知 → 调 `payment-report`（结构化字段）。秒级、可控、能做多账号；代价是要维护一个常驻 App。

### 5.3 不推荐 / 兜底

| 方案 | 评价 |
| --- | --- |
| 语音播报 + 语音识别 | 准确率差，只作兜底 |
| wechaty 等协议 Hook | **不推荐**：违反微信用户协议，封号风险 |
| 账单导出对账 | 非实时，只做事后核对 |

## 5.4 Token 鉴权的边界（重要）

转发工具算不出 HMAC 签名（需要时间戳 + nonce + 摘要），所以上报接口额外支持一枚长期 Token：

- 走 `X-Monitor-Token` 请求头或 `?token=` 参数（后者给只能配 URL 的工具用）。
- Token 只能调用上报接口，不能下单 / 查单 / 退款。
- 最坏后果：Token 泄露者只能把**该商户自己**处于待支付、且金额对得上的订单点成已付 —— 不跨商户、不碰别人的钱。
- 后台可随时重置，重置即旧 Token 立即失效。

## 6. 配置项（后台「系统设置」热更新，无需重启）

| Key | 默认 | 说明 |
| --- | --- | --- |
| `personalQr.autoConfirm` | `true` | 关闭则全部到账需人工确认 |
| `personalQr.matchWindowMinutes` | `30` | 匹配时间窗 |
| `personalQr.uniqueAmount` | `false` | 唯一金额识别码 |
| `personalQr.textAmountRegex` | 空 | 到账文本上报的自定义金额正则（第一个捕获组为金额） |
| `alert.personalQrUnmatched` | `true` | 挂账告警邮件 |

## 7. 风险与合规提示（务必知悉）

1. **资金不受支付中心托管**：个人码收款不进入受监管的商户账户，无法自动退款、无法渠道对账，退款只能人工原路退回。
2. **账号风控**：个人收款码高频/固定金额收款可能触发微信/支付宝风控（限制收款、冻结），需控制频次与金额、多码轮换。
3. **通知监听的脆弱性**：手机断网、App 被杀、通知格式变更都会漏报；必须有**挂账告警 + 人工兜底**流程（本方案已内置）。
4. **合规**：个人码经营性收款在监管口径上属于「个人转账」，与《条码支付业务规范》的商户收款要求存在差异。
5. **推荐替代**：若业务量起来，优先入网
   - **微信支付小微商户**（无营业执照也可入网，Native/JSAPI，官方回调）
   - **支付宝当面付**（个体户执照）
   - **银行聚合收款码 / 持牌聚合支付**（有 API 回调）

   这些渠道在支付中心里接上适配器即可，**业务系统代码零改动**，且拥有真正的官方回调与对账能力。
